# CLK 2.5.0 Worker Wake, Run Patrol, and Layered Progress Design

## Status and authority

This design implements the five Owner-approved hard rules for CLK 2.5.0. It is
limited to fixed persistent Chains, ordered Levels, full Barriers, and their
existing D0/D1/D2/LEVEL/D3 authorities. It does not modify LCCoding, Calabash,
SLK, GLK, or any other repository. The Owner has already approved the requirements
and directed implementation to continue after this document and its plan pass
self-review.

## Goals

1. Give only a Worker a bounded four-level way to wake its originally bound
   Checker after the current formal CELL delivery, BLOCKED result, or execution
   failure.
2. Prohibit Supervisor from remaining online through `wait_threads`; bounded
   Worker ACK waits are the sole exception.
3. Give every Run exactly one visible, non-authoritative mechanical patrol
   conversation and exactly one patrol heartbeat.
4. Define subtask, visible task, and subagent precisely enough for mechanical
   enforcement without treating GO/CELL/Round work as an agent.
5. Add layered real-time progress reporting whose numerators come only from valid
   D1 Receipts, D2 verdicts, Level transitions, D3, and Owner Acceptance.

## Non-goals

- No general role-to-role message bus.
- No wake ladder for Checker, Verification, Supervisor, Router, Grapher, patrol,
  or Owner.
- No new technical-verdict role, D layer, topology, dynamic routing, or Runtime
  state machine.
- No patrol code review, plan review, product work, repair, dispatch, acceptance,
  or engineering-progress reporting.
- No Supervisor CELL feed and no Verification continuous progress feed.
- No real sleeps in tests and no remote operations in this release task.

## Architectural choice

CLK 2.5.0 uses one content-addressable control trace format outside the mutable
Runtime index. The trace is an auditable simulation and validation package, not a
new execution method or authority. A single schema/template/validator pair covers
the liveness and progress invariants so the same Worker wake identity cannot drift
between retries or disagree with the progress denominator.

The alternatives were rejected:

- Adding wake/patrol fields to `runtime-state-index` would turn a coordination
  safeguard into Runtime state.
- Separate wake, patrol, and progress schemas would duplicate Run, binding,
  Required-set, clock, and event identity and create cross-file drift.
- Prose-only rules would not mechanically reject disabled capabilities, stale
  denominators, or delivery-as-acceptance errors.

The native package is:

- `run-control-trace.schema.json`: structural fail-closed envelope;
- `run-control-trace.yaml`: one valid Level-1 wake and layered-progress example;
- `validate_run_control.py`: cross-event and authority invariants;
- `worker-wake-patrol-and-progress.md`: the single detailed operational
  reference used by compact SPEC/SKILL clauses;
- `test_run_control.py`: injected-clock simulations and optimized-mode negatives.

## Hard rule 1: Worker-only four-level wake ladder

### Frozen binding and preflight

Before Checker dispatches a formal Round, the binding freezes:

- Worker ID and role;
- paired Checker ID, `checker_thread_id`, and `checker_host_id`;
- Run, Chain, GO, CELL, CELL ordinal, current Required CELL total, Round, and
  Required-set version;
- Worker capability evidence for send, read, list, unarchive, deterministic
  temporary-heartbeat upsert/delete, and PENDING_WAKE write.

Every capability is required. Missing or disabled capability fails before formal
dispatch. A later Level-2 host repair may use only the same Checker's frozen role
registry entry. It may not guess an ID or create a replacement Checker.

### Scoped signal

The Worker signal is short and mechanically scoped. Delivery uses the canonical
shape:

```text
GO-03-A CELL 25/30 已交付，请检查
```

BLOCKED and EXECUTION_FAILURE use the same GO/CELL `n/N` identity and name the
condition. `25` is the current Required CELL position, not an accepted count.
Rework retains the CELL ordinal and changes only the Round identity.

### Injected-clock escalation

The trace uses integer injected minutes. No implementation or test sleeps.

1. T+0: Worker sends to the frozen thread and host, then permits at most two
   injected minutes for ACK or mechanical processing evidence.
2. T+2: Worker reads/lists the original conversation; it may correct erroneous
   archive state or resolve the same Checker from the frozen role registry and
   resend the identical scoped signal.
3. T+4: Worker upserts one deterministic temporary Checker heartbeat. This action
   does not create a conversation. Checker ACKs first and deletes the heartbeat.
4. T+6: Worker writes one deterministic PENDING_WAKE binding all identities,
   three attempts, errors, and timestamps. Best-effort notification is optional;
   the unique patrol must discover the record independently.

A scope-matching `WAKE_ACK` or mechanical evidence that the same Checker began
processing stops escalation immediately. All later attempts are forbidden.
Temporary heartbeat and PENDING_WAKE state are deleted, closed, or consumed
idempotently. No success path creates duplicate implementation or validation.

Checker must make `WAKE_ACK` its first action for the wake and bind Run, GO, CELL,
and Round. It then emits `收到 GO-X CELL n/N，开始检查` before D1 work.

## Hard rule 2: Supervisor wait boundary

Supervisor never calls `wait_threads` as an online wait, never loops it, and never
waits for all Workers. Read/list and `timeoutMs: 0` snapshots are non-waiting
observations and remain allowed. Supervisor ends its turn after a dispatch or
control action. Only Worker may perform the four bounded ACK windows above.

Any Supervisor `wait_threads` event is an invalid trace and a patrol alert
condition. The validator does not accept a timeout value, loop flag, or stated
reason as a waiver.

## Hard rule 3: exactly one Run patrol

Each Run binds exactly one visible `RUN_PATROL_CONVERSATION` and one heartbeat.
The binding is fixed to:

```text
model = gpt-5.6-luna
reasoning_effort = xhigh
interval_minutes = 10 | 15 | 30
```

The frozen Run difficulty selects the interval. Patrol is a non-authoritative
mechanical conversation, not a product or technical-verdict role, and therefore
does not expand the existing CLK role type or D-layer lists.

Patrol checks only:

- unexplained lack of legal progress;
- unconsumed PENDING_WAKE;
- evidence of `spawn_agent`, `delegate_task`, hidden Agent, or background Agent;
- Supervisor `wait_threads`;
- duplicate patrol conversation or heartbeat;
- patrol left open after formal Loop termination.

RUNNING, formal PAUSED, legitimate BLOCKED, and documented external-condition
waits are distinct. Patrol may emit only fixed status, evidence, and alerts. It
cannot inspect code quality, judge plans or acceptance, repair, take over, or
redispatch. It cannot call create/fork/spawn/delegate operations.

After formal termination it must prove this order:

```text
LOOP_TERMINAL confirmed
→ patrol heartbeat deleted
→ PATROL_CLOSED
→ patrol conversation archived
```

## Hard rule 4: task and subagent definitions

- Subtask: a GO, CELL, Round, plan step, or other scoped unit of work.
- Visible peer task: a sidebar-visible same-project conversation with a stable
  thread ID. It is not a subagent merely because it receives a subtask.
- Subagent: only `spawn_agent`, `delegate_task`, hidden Agent, or background Agent.

The validator allows text containing `子任务` and evidence for a visible peer task.
It rejects actual subagent-capability evidence. Patrol, schema, readiness, and
simulation all use this same definition.

## Hard rule 5: layered real-time progress reporting

### Worker to Checker

Every wake level reuses one progress identity and one scoped signal. Delivery,
BLOCKED, or EXECUTION_FAILURE does not modify an accepted count.

### Checker local progress

Checker is the finest progress authority. It ACKs first, announces inspection, and
then derives `accepted_cell_count` from unique, current, effective D1 PASS Receipts
for the current Required-set version:

- PASS: `GO-X CELL验收 a/N` and next-CELL or candidate state;
- FAIL/REWORK: `a/N` is unchanged and the same CELL enters a new Round;
- BLOCKED: `a/N` is unchanged and the blocker is shown.

Worker delivery, green Worker tests, inspection start, duplicate Receipt, and
rework Round do not increment. A CELL ID contributes at most once.

### Checker to Supervisor

Checker sends no CELL stream to Supervisor. It emits a GO milestone only after all
current Required CELLs have valid D1 PASS and the immutable candidate reaches a GO
boundary. `GO_CANDIDATE_READY`, `VERIFYING`, and `D2_VERIFIED` are distinct. The
milestone shows GO ordinal/Required GO total and `CELL N/N` accepted.

### Supervisor global progress

Supervisor emits one concise update only after a substantive GO, Level, frozen
Graph/manifest Required-set, Run, D3, or Owner-Acceptance state change. It reports:

- current Level D2-verified Required GOs / current Level Required GOs;
- verified Levels / total Required Levels;
- the current hierarchical status and Required-set version.

CELL means D1 accepted, GO means D2 verified, Run verified means current D3 PASS,
and Owner accepted means the bounded Owner verdict. Unverified same-Level GOs and
Worker deliveries never enter a numerator. A frozen Graph/manifest version may
change a Required set, but this is not GLK routing or a Grapher role.

Verification emits formal verdicts only. Patrol emits no engineering progress.
Router/Grapher boundaries remain external and unchanged.

### Amendments and historical truth

Every denominator comes from one versioned Required set. Baseline, manifest, or
frozen graph amendment activates a new Required-set version and explicitly lists
preserved current Receipt/verdict identities. The validator recomputes all
denominators and numerators from that version. Historical events remain immutable.

The controlled state vocabulary is:

```text
DELIVERED
D1_ACCEPTED
GO_CANDIDATE_READY
D2_VERIFIED
RUN_VERIFIED
OWNER_ACCEPTED
```

Generic `completed` cannot substitute for these states.

## Validator model

The control trace contains one Run binding, versioned Required sets, fixed
Worker/Checker bindings with capability preflight, exactly one patrol binding, and
an injected-time event stream. The validator first applies JSON Schema and then
replays events in sequence. It derives wake escalation, cleanup, D1 accepted CELL
sets, candidate readiness, D2 verified GO sets, Level completion, and Run/Owner
states rather than trusting free-text counters.

The validator uses explicit exceptions and condition checks, never Python
`assert`, so `python -O` preserves fail-closed behavior.

## Acceptance scenarios

The TDD suite must prove:

1. Level 1 succeeds and later levels do not run.
2. Level 1 fails and Level 2 succeeds at T+2.
3. Level 2 repairs erroneous archive/host using the same frozen Checker.
4. Thread-not-found never guesses identity or creates a replacement.
5. Level 3 heartbeat is deterministic, unique, and deleted after ACK.
6. Three failures produce PENDING_WAKE at T+6 and unique patrol consumption.
7. Matching ACK stops escalation; mismatched ACK does not.
8. A non-Worker wake attempt fails.
9. Supervisor wait fails while zero-time snapshots pass.
10. Visible task and `子任务` text pass; spawn/delegate/hidden/background evidence
    fails.
11. Formal pause is not alerted as a stall.
12. Duplicate patrol or heartbeat fails.
13. Terminal cleanup order and archive are mandatory.
14. Missing Worker capabilities fail before dispatch.
15. Worker messages carry GO/CELL `n/N` and all wake levels keep one identity.
16. Delivery, FAIL, BLOCKED, duplicate Receipt, and rework do not increase D1
    accepted count; one effective D1 PASS increments once.
17. Candidate ready does not equal D2 verified.
18. Checker sends milestones only at GO boundaries.
19. Supervisor counters match current CLK Level topology and valid D2/Level
    evidence.
20. Required-set amendment changes the visible version and recomputes denominators.
21. Supervisor does not rebroadcast Worker/CELL noise.
22. Critical invalid traces fail in normal and `python -O` execution.

## File and compatibility policy

The release updates VERSION, canonical SPEC/SKILL/reference, control contract,
agent prompt, readiness bank/key without increasing the fixed 25-question count,
launch simulation requirements, schema/template/validator/tests, repository and CI
gates, Manifest/hash, README/CHANGELOG/migration/report, and Run receipt version.

Existing topology, role authorities, D0-D3 Receipts, Barrier semantics,
topology-fault localization, maximum-valid-Chain definition, and LCCoding boundary
remain unchanged. Active 2.4.0 Runs remain on 2.4.0; migration occurs only at a
safe boundary with fresh 2.5.0 readiness and simulation evidence.

## Self-review result

- Placeholder scan: no unresolved marker or deferred requirement.
- Consistency: one control trace is explicitly outside Runtime; patrol is a visible
  non-authoritative conversation and does not alter technical role enums.
- Scope: all five hard rules are covered without adding cross-method behavior.
- Ambiguity: Worker wait timing is exact injected T+0/T+2/T+4/T+6; progress
  numerators and denominators have one declared evidence source each.
