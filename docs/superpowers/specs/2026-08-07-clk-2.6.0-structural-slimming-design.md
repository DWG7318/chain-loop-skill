# CLK 2.6.0 Structural Slimming Design

Date: 2026-08-07
Status: accepted under Owner-delegated implementation authority

## Problem

The canonical installed `chain-loop-skill/SKILL.md` has reached the governed
1000-line Markdown ceiling. Much of the file restates detailed material that already
has a narrower canonical home under `chain-loop-skill/references/`. This makes every
CLK activation load the complete operating manual even when a Run needs only the
method boundary and the relevant reference.

The Python production surface is about 2,581 physical lines and already separates
plan, receipt, runtime, run-control, topology-fault, model-policy, readiness, and
repository validation. No duplicate runtime authority or unreachable implementation
justifies splitting those validators in this release.

## Goal

Reduce the canonical installed Skill to at most 650 physical lines while preserving
all CLK behavior, authority boundaries, machine-readable contracts, validators,
templates, readiness content, and detailed reference material.

## Non-goals

- No role, receipt, state, route, verification layer, Chain, Level, or barrier change.
- No change to the model policy, Worker wake ladder, Patrol, progress, capacity, or
  Pin rules.
- No validator or schema split merely to reduce a line count.
- No deletion or reinterpretation of historical MSLK evidence.
- No version change beyond the already completed 2.6.0 candidate.

## Considered approaches

### Keep the 1000-line Skill

This has the lowest immediate editing risk but leaves no space for future corrections
and keeps repeated reference details in every activation context. Rejected.

### Mechanically split validators and documents

This would create more files without reducing authority or behavior. It increases
navigation and release surfaces. Rejected.

### Kernel Skill with routed references

Keep the always-loaded Skill as the executable method kernel. Preserve identity,
selection, topology, hard rules, role authority, lifecycle, required gates, critical
runtime safeguards, completion criteria, recovery boundary, and launch checklist.
Route detailed construction and operational procedures to the existing references.
Selected.

## Canonical Skill boundary

The slim Skill must retain, in one readable path:

1. canonical identity, trigger, and exclusive-method lock;
2. fixed Chain/Level/full-barrier topology and method-selection proof;
3. the full hard-rule set without weakening or renumbering its meaning;
4. Supervisor, Checker, Worker, and fresh GO Verification authority;
5. Calabash, readiness, simulation, Level-start, autonomy, and isolation gates;
6. CELL execution, direct Verification handoff, Level barrier, and final audit flow;
7. topology-fault, model-binding, Worker wake, Patrol, progress, capacity, and Pin
   safeguards at policy level;
8. append-only evidence, Markdown boundary, recovery, LCCoding boundary, and
   publication gate;
9. direct links to every detailed canonical reference required to execute those
   policies.

The Skill must not duplicate full field lists, scenario enumerations, record layouts,
or long procedural explanations already maintained by a linked reference, schema,
template, or validator.

## Reference ownership

- `calabash-and-chain-loop.md`: Calabash construction and Chain/Level semantics.
- `role-isolation-and-verification.md`: role, context, workspace, and evidence
  isolation plus direct fresh Verification.
- `model-selection-and-binding.md`: selectable model classes, equivalence evidence,
  and rebinding.
- `worker-wake-patrol-and-progress.md`: Worker-only wake ladder, Patrol, progress,
  capacity, task/subagent distinction, and Pin rules.
- `topology-fault-localization.md`: fault classes, causal localization, minimal
  reverification, and stop conditions.
- `checker-detection-catalog.md`: detection tiers and receipts.
- `run-lifecycle-and-verification.md`: lifecycle and verification economy.
- `receipt-and-state-contracts.md`: receipt, mutable index, barrier, and amendment
  structure.
- `clk-control-operations.md`: start, pause, resume, Level, direct handoff, and
  safeguard operations.
- `lccoding-interface.md`: outer method boundary.

## Compatibility and failure handling

Machine artifacts remain unchanged. Existing tests continue to define runtime
behavior. A new repository test fails when the canonical Skill exceeds 650 lines,
loses any kernel section, or stops linking a required reference. Any such failure
blocks the release candidate.

The root historical `SKILL.md` remains migration evidence and is not the installed
CLK entrypoint. This slice does not rewrite historical MSLK meaning.

## Acceptance

- canonical installed Skill is 650 lines or fewer;
- every kernel section and required reference link is present;
- full pytest and optimized critical tests pass;
- all repository, plan, runtime, topology, run-control, model-policy, Receipt, and
  readiness validators pass;
- `FILE_HASHES.json`, Manifest identity, Git diff, and worktree cleanliness pass;
- no production Python, schema, template, or reference behavior changes.
