# CLK 3.0.0 Reconstruction Design

## Status

- Design status: Owner-approved in conversation
- Target version: `3.0.0`
- Method: Chain Loop Skill (`CLK`)
- Base method: Small Loop Skill (`SLK`) `3.0.0`
- Design direction: reconstruct instead of extending the 2.x control kernel

## 1. Decision

CLK 3.0.0 is an orchestration extension of SLK.

It does not define a second engineering method for Checker and Worker. It uses one
shared Supervisor to organize two or more concurrently running SLK construction
Chains and, after every required construction Chain passes its own D2, one final
Fusion Chain that also works as SLK.

The compact definition is:

> One CLK Run consists of two or more concurrent SLK construction Chains followed
> by one Fusion SLK Chain.

The originating planning conversation uses CLK to establish the Run and obtain
Owner confirmation. After handoff, the Supervisor uses CLK to orchestrate the Run.
Checker and Worker continue to use SLK.

CLK never calls an SLK child Skill as a free-standing procedure. For each
construction or Fusion Chain, CLK first enters an explicitly scoped SLK execution
context through the SLK main Skill; the SLK main Skill then routes the relevant SLK
child Skill. The project-level selected method remains CLK, while the Chain-level
execution method is SLK.

## 2. Core topology

```text
                         shared Supervisor
                    /           |           \
          Chain A (SLK)   Chain B (SLK)   Chain C (SLK)
          Checker A       Checker B       Checker C
              <->             <->             <->
          Worker A        Worker B        Worker C
              \               |               /
                  each Chain passes D2
                            |
                   Fusion Chain (SLK)
                   new Checker <-> new Worker
                            |
                     final Run D2
```

One construction Chain contains one or more linearly ordered GOs. Each GO contains
appropriately sized linear CELLs under SLK.

The Fusion Chain is created once, but may contain one or more linearly ordered
Fusion GOs. "One fusion" means one final Fusion Chain and one continuous fusion
sequence, not one GO.

CLK 3.0.0 has no Stage or Level model and no repeated synchronization barrier.

### 2.1 Canonical lifecycle and communication graph

```text
originating conversation <-> Owner
          |
          +-> enter CLK
          |     +-> plan current Run
          |     +-> design fusion contracts
          |     +-> design temporary parallel isolation
          |     +-> call SLK planning/model guidance where needed
          |
          +-> Owner confirms this Run
          |
          +-> create new Supervisor <-> communication test
                                      |
                                      +-> read CLK
                                      +-> CLK routes to SLK
                                      +-> SLK Supervisor Grill
                                      +-> CLK Supervisor Grill
                                      +-> initialize CLK and Chain records
                                      |
                    +-----------------+-----------------+
                    |                 |                 |
             create Checker A  create Checker B  create Checker C
                    <-> test          <-> test          <-> test
              SLK Checker      SLK Checker       SLK Checker
              understanding    understanding     understanding
                    |                 |                 |
             creates Worker A  creates Worker B  creates Worker C
                    <-> test          <-> test          <-> test
                    |                 |                 |
             Supervisor <-> Worker emergency-channel tests
                    |                 |                 |
                    +--------- all pairs ready ---------+
                                      |
                          start all construction Chains
                                      |
              Chain A SLK       Chain B SLK       Chain C SLK
              D0 -> D1          D0 -> D1          D0 -> D1
                    \                 |                 /
                     clean Chain handoffs activate shared Supervisor
                                      |
                         independent Chain D2 decisions
                                      |
                       all required Chain handoffs frozen
                                      |
        Supervisor first finalizes Fusion GO/CELL/model plan through SLK guidance
                                      |
              Supervisor <-> new Fusion Checker <-> new Fusion Worker
                    \------------- emergency -------------/
                                      |
                           Fusion SLK: D0 -> D1 -> D2
                                      |
                         archive members and report Owner
```

After Supervisor handoff, the originating conversation exits engineering and
checking work. It keeps only the SLK-defined Owner-contact and Supervisor-recovery
entry.

## 3. Scope and method selection

CLK is intended for a medium or large engineering Run that can be divided into at
least two genuinely independent construction Chains.

A valid construction Chain:

- has a stable responsibility boundary;
- has its own linear GO path;
- can begin in the same construction cycle as every other construction Chain;
- does not need another construction Chain's unfinished internal result;
- can work in an isolated temporary environment; and
- can deliver a result conforming to a complete fusion interface contract.

All construction Chains start in the same construction cycle and progress in
parallel. If the work can only be performed by completing one whole Chain before
starting the next, SLK is the more appropriate method.

The number of Chains is chosen from the computer, models, shared resources, and
engineering load that can be supported concurrently. The plan does not create more
Chains than the available environment can run in parallel.

## 4. Multiple CLK Runs in one project

A project may contain multiple CLK Runs in chronological order:

```text
CLK Run 1: finalize -> Owner confirms -> concurrent Chains -> Fusion -> D2
CLK Run 2: finalize from Run 1 delivery baseline -> Owner confirms -> ...
CLK Run 3: finalize from Run 2 delivery baseline -> Owner confirms -> ...
```

Future Runs may be preplanned as a roadmap, but a preplan is not an established or
active Run. After the preceding Run completes, the next Run is formally finalized
from the new real delivery baseline and confirmed by the Owner before it starts.

Every CLK Run:

- has one Run objective;
- receives its own Owner confirmation;
- creates a new Supervisor;
- has one set of concurrent construction Chains;
- has one Fusion Chain; and
- ends with one final D2 conclusion.

The Supervisor of a completed Run does not own the next Run.

## 5. Role model

CLK adds no role type. The only roles are the SLK roles:

- Supervisor;
- Checker; and
- Worker.

One CLK Run shares one Supervisor. Each construction Chain has a fixed, independent
Checker and Worker pair. The Fusion Chain receives a new Checker and Worker pair
after its inputs are ready.

### 5.1 Supervisor

The shared Supervisor is the only role whose responsibilities differ from ordinary
SLK. It understands both CLK and SLK and is responsible for:

- validating the Owner-confirmed Run plan;
- understanding the Chain decomposition;
- understanding and governing fusion interface contracts;
- provisioning the parallel isolation plan;
- creating one Checker for every construction Chain;
- starting all construction Chains in the same construction cycle;
- responding to Chain-level events without following ordinary CELL traffic;
- performing each construction Chain's D2;
- freezing D2-passed Chain handoffs;
- finalizing and starting the Fusion Chain;
- performing the Fusion Chain's final D2;
- maintaining the CLK Run record; and
- archiving completed Checker and Worker conversations.

The Supervisor does not take over ordinary CELL planning, dispatch, D1, or Worker
rework. It is event-activated and does not wait online or use Patrol.

### 5.2 Checker and Worker

Checker and Worker follow SLK without CLK-specific role rules.

They read:

1. the SLK Skill relevant to their role and current situation;
2. their assigned Chain plan; and
3. the fusion interface contract that their work must satisfy.

They do not need to read the CLK Skill or understand other Chains' internal work.

## 6. Entry and readiness order

The activation order is:

```text
Supervisor reads CLK
        |
CLK declares and routes its SLK dependency
        |
Supervisor reads and understands SLK
        |
Supervisor passes the SLK Supervisor Grill
        |
Supervisor returns to the CLK-specific extension
        |
Supervisor passes the CLK Grill
```

The CLK Grill checks practical understanding of:

- why the selected Chains are independent;
- each Chain's responsibility boundary;
- the complete fusion interface contracts;
- the temporary parallel isolation plan;
- construction Chain D2 scope;
- the Fusion Chain start condition; and
- contract-conflict handling.

Checker and Worker use the existing SLK understanding and readiness flow.

## 7. Run planning and Owner confirmation

Before the new Supervisor is created, the originating conversation and Owner settle
the current Run plan.

The plan contains six core outputs:

1. Run objective, scope, and final outcome;
2. two or more independent construction Chains;
3. each Chain's linear GOs and initial CELL plan;
4. complete fusion interface contracts and executable contract checks;
5. a temporary parallel isolation and resource plan; and
6. the Fusion Chain objective, required inputs, outcome, and provisional GO outline.

Initial CELL sizes consider the assigned models, actual computer capacity, shared
load, engineering complexity, and reserve capacity. Review uses the SLK D0, D1,
and D2 layers and avoids needless repetition.

The planning conversation enters the SLK main Skill for every planned construction
Chain and lets SLK route its planning and model-selection Skills for the shared
Supervisor and every planned Checker/Worker pair. CLK adds no model policy. Owner
model choices remain valid under SLK.

The Owner confirms the formal plan and start of every CLK Run. After the Supervisor
is created, the originating conversation and Supervisor complete a two-way
communication test and transfer the complete handoff. The originating conversation
then exits the Run's engineering and checking work while retaining the recovery
entry described in Section 2.1.

This one Owner-confirmed CLK plan selects SLK as the execution method for every
listed construction Chain and the later Fusion Chain. It does not ask the Owner to
repeat method selection or start approval for each subordinate Chain.

## 8. Fusion interface contracts

Fusion interface contracts are central CLK artifacts, not brief interface notes.
Every construction Chain works against the current applicable contract.

Depending on the project, a contract records:

- provided and consumed capabilities;
- APIs, functions, MCP tools, events, or call patterns;
- schemas, fields, types, and examples;
- state and lifecycle behavior;
- errors, exceptions, and failure responses;
- permission, security, and sensitive-data boundaries;
- persistence, sharing, and consistency requirements;
- versioning and compatibility behavior;
- performance, resource, and concurrency requirements;
- how the Fusion Chain consumes the result;
- executable contract tests, schemas, fixtures, mock consumers, and expected
  results; and
- final deliverables and Chain D2 acceptance conditions.

The originating conversation prepares the initial contracts during Run planning.
The Supervisor checks that they are complete and executable before creating
Checkers.

If engineering evidence shows a technical contract defect, the Checker reports the
facts and recommendation to the Supervisor. Within the Owner-confirmed Run outcome,
the Supervisor may create a recorded contract revision and coordinate every affected
Chain. A product-goal, business-choice, or Owner-authority change returns to the
Owner as one clear question.

No role silently changes a shared interface. Chain D2 uses the current contract
version.

## 9. Temporary parallel isolation

The governing principle is:

> Logical contracts remain stable; physical construction isolation is temporary
> and injected.

Temporary isolation supports parallel work without becoming part of the product
architecture.

| Formal contract identity | Temporary construction binding |
|---|---|
| service or module identity | process or instance name |
| API and call semantics | port and address |
| data model and storage rules | database, schema, or data copy |
| file and cache semantics | directory and cache location |
| permission boundary | test account, token, or local setting |
| code and delivery boundary | worktree and construction branch |
| observability behavior | log directory and instance identifier |
| user-session behavior | browser profile or test user |

Temporary values are injected through configuration, environment variables, or
test fixtures. They do not become fixed product interface values unless the fusion
interface contract explicitly defines them as permanent product identity.

Each construction Chain normally receives an independent temporary worktree,
branch, output directories, mutable data, runtime bindings, logs, caches, and
resource allocation. Read-only immutable dependencies may be shared.

Chain D2 checks that the result can leave its temporary environment and be deployed
and called through the formal contract. The Fusion Chain receives code, frozen
artifacts, contracts, and required data, not mutable construction residue. It uses
a new integration worktree and determines the complete system's final runtime
configuration.

Short access to a genuinely non-replicable physical resource may be coordinated,
but it does not turn whole Chains into sequential execution.

## 10. Construction, D2, and Fusion

### 10.1 Construction Chains

Every construction Chain follows SLK:

```text
Worker D0 -> Checker D1 -> shared Supervisor D2 for this Chain
```

Checker handles daily GO/CELL dispatch, D1, rework, progress, and communication
recovery. Supervisor does not follow each CELL.

Supervisor is activated when:

- a Chain is ready for D2;
- a Chain reports an issue that SLK cannot resolve internally;
- a fusion contract needs recorded revision;
- a member needs Supervisor-level recovery or replacement; or
- every required construction Chain has passed D2.

### 10.2 Chain D2

Construction Chain D2 checks both:

1. whether the Chain's GOs compose correctly; and
2. whether the frozen Chain result fully conforms to its fusion interface contract.

It uses the executable contract material and checks the deliverable, version,
commit or artifact identity, portability out of the temporary environment, and
handoff record.

The Checker initially hands the shared Supervisor a clean Chain D2 package: Chain
objective, GO outcomes, frozen candidate, end-to-end entry, applicable fusion
contract, and necessary objective environment facts. The package does not lead with
D0 conclusions, D1 conclusions, rework history, or Checker persuasion.

The Supervisor first forms an independent D2 judgment from the candidate, contract,
and observable composition. It then reads the detailed D0, D1, rework, exemption,
and record history to find omitted facts and verify record consistency. This keeps
SLK D2 isolation while allowing one shared Supervisor to inspect multiple Chains.

A D2 failure returns to the same Chain's SLK rework flow. Other independent Chains
continue. A result becomes a formal Fusion input only after Chain D2 passes.

After D2 passes, the Supervisor freezes the handoff identity, records it, and
archives the completed Checker and Worker conversations.

### 10.3 Fusion Chain

After every required construction Chain passes D2, the Supervisor:

1. uses the real frozen inputs to finalize the Fusion GO list and initial CELL plan;
2. enters the SLK main Skill and uses SLK planning and model-selection guidance for
   the Fusion Chain;
3. creates a new integration worktree and branch;
4. creates a new Fusion Checker and completes the Supervisor-to-Checker two-way
   communication test;
5. completes the SLK Checker understanding confirmation;
6. lets that Checker create a new Fusion Worker and completes the
   Checker-to-Worker two-way communication test;
7. completes the Supervisor-to-Worker emergency-channel test; and
8. starts the Fusion Chain as SLK.

The Fusion Chain may contain one or more linear GOs and appropriately sized CELLs.
Its purpose is to compose already contract-conforming Chain results into one real
system. Its D2 is the final D2 of the CLK Run; CLK adds no higher verification layer.

## 11. Skill architecture

CLK 3.0.0 uses one main Skill and eight small role-scoped child Skills:

```text
$chain-loop-skill
|
+-- $clk-plan-run
|   +-- $clk-design-fusion-contracts
|   +-- $clk-plan-parallel-isolation
|
+-- $clk-grill-supervisor
+-- $clk-launch-chains
+-- $clk-complete-chain
+-- $clk-start-fusion
+-- $clk-close-run
```

### 11.1 Main Skill

`$chain-loop-skill` is the only CLK entrypoint. It defines the method and routes the
originating planning conversation or the Supervisor to the required CLK child
Skill. During Supervisor takeover, it also routes the Supervisor to SLK.

### 11.2 Child Skills

- `$clk-plan-run`: establish the current Run, Chain plan, initial GO/CELL plan,
  Fusion outline, and Owner confirmation.
- `$clk-design-fusion-contracts`: create complete contracts and executable contract
  checks.
- `$clk-plan-parallel-isolation`: allocate temporary isolation and concurrent
  resources without leaking them into product contracts.
- `$clk-grill-supervisor`: route through the SLK Supervisor Grill and then confirm
  CLK-specific understanding.
- `$clk-launch-chains`: create Checkers, complete the SLK Checker understanding
  confirmation, let Checkers create Workers, test all SLK communication routes,
  and start all construction Chains in one construction cycle.
- `$clk-complete-chain`: apply SLK D2 to one completed construction Chain, freeze
  its Fusion handoff, and archive its members. It changes only the outer closure
  destination: a construction Chain conclusion enters the CLK record and Fusion
  input set instead of becoming an Owner-facing completed Run conclusion.
- `$clk-start-fusion`: finalize Fusion GOs and initial CELLs from D2-passed inputs,
  route through SLK planning/model guidance, and start the new Fusion SLK pair in a
  new worktree.
- `$clk-close-run`: complete final D2, archive Fusion members, keep the Supervisor,
  and report the Run conclusion without starting another Run.

Each CLK child Skill states that it is a CLK child Skill for the current CLK Run
and is not used independently. Planning, contract, and isolation Skills are used by
the originating planning conversation before Supervisor handoff. Grill, launch,
completion, Fusion, and closure Skills are used by the CLK Supervisor. Checker and
Worker continue to use SLK Skills.

## 12. Records, progress, and handoff

The Supervisor creates at project root:

```text
CLK-RUN-<RUN-ID>-RECORD.md
```

The record is the readable Run entrypoint. It contains:

- Owner-confirmed objective and start;
- Chain roster and responsibilities;
- contract and isolation-plan locations and versions;
- role and worktree identities;
- Chain-level progress;
- Chain D2 conclusions and frozen handoffs;
- contract revisions, errors, rework, and exemptions;
- Fusion GO progress and final D2;
- archive state; and
- the final Run conclusion.

Each construction Chain also receives its own SLK-compatible root record:

```text
SLK-RUN-<RUN-ID>-CHAIN-<CHAIN-ID>.md
```

The Fusion Chain receives:

```text
SLK-RUN-<RUN-ID>-FUSION.md
```

Worker, Checker, and the shared Supervisor use the applicable Chain record according
to SLK. Separate Chain files avoid concurrent record writes from unrelated Chains.
The CLK record is a Supervisor-owned Run summary and never replaces those SLK
records.

Detailed artifacts use:

```text
coordination/clk/<RUN-ID>/
  contracts/
  isolation/
  chains/
    CHAIN-A/
    CHAIN-B/
  fusion/
```

Within a Chain, every role records its own facts before handing off, as required by
SLK. The CLK root record contains conclusions and links, not copied transcripts or
duplicate evidence.

The Owner receives one concise completion conclusion and the record path, for
example:

```text
CLK Run completed.
3/3 construction Chains passed D2; the Fusion Chain passed final D2.
Exemptions: 1.
Complete record: <path>
```

## 13. Continuity and recovery

CLK inherits SLK communication, rework, exemption, recovery, and archive behavior.

- Worker failure is handled by its Checker.
- Checker failure is handled by the shared Supervisor.
- Worker-to-Checker communication recovery follows the SLK emergency route
  `Worker -> shared Supervisor -> owning Checker` and always carries the Chain ID.
- There is no direct Checker-to-Checker or Worker-to-Worker operating route.
- CELL or D1 failure remains inside the owning Chain's SLK flow.
- Chain D2 failure returns only to the owning Chain unless a contract revision
  mechanically affects another Chain.
- Ordinary engineering problems go to the Supervisor, not the Owner.
- The Supervisor does not remain online waiting for members.
- CLK has no Patrol role or heartbeat loop.

Owner involvement is reserved for the formal establishment and start of every CLK
Run and for genuine product-goal, business-choice, or Owner-authority decisions.

## 14. Retired 2.x architecture

The following do not belong to the 3.0.0 active kernel:

- Stage and Level;
- full-Level barriers;
- GO-scoped Verification roles;
- Patrol and heartbeat inspection;
- fixed models and model-binding ledgers;
- fixed-count readiness Evals;
- the independent Detection system;
- the Topology Fault state machine;
- Pin control;
- complex wake timelines;
- pre-created Verification conversations; and
- duplicated CLK definitions of Checker, Worker, CELL, rework, model choice, or
  record behavior already owned by SLK.

Old releases remain Git history only. CLK 3.0.0 is the current method and does not
carry a parallel 2.x operating kernel.

## 15. Acceptance criteria

CLK 3.0.0 is accepted when:

- the main Skill explains "concurrent SLK construction Chains plus one Fusion SLK"
  at a glance;
- only the originating planning conversation and Supervisor read CLK;
- CLK loads and verifies SLK understanding before CLK-specific understanding;
- every Chain enters through the SLK main Skill before an SLK child Skill is used;
- Checker and Worker receive no CLK-specific role method;
- the graph contains exactly one Supervisor and no implied Chain Supervisor;
- the originating conversation, Supervisor, Checker, and Worker communication and
  recovery routes match SLK;
- two-Chain, three-Chain, and unequal-length Chain examples are representable;
- all construction Chains start in the same construction cycle;
- Fusion supports one or more linear GOs;
- Fusion initial CELL and role-model planning completes before the Fusion Checker is
  created;
- contract revision and Chain D2 rework are supported without adding roles;
- executable contract checks are part of Chain D2;
- Chain D2 preserves SLK input isolation and does not send an intermediate Owner
  completion conclusion;
- every construction Chain and the Fusion Chain has its own SLK-compatible record;
- temporary isolation does not leak into formal contracts;
- sequential project Runs require a new Supervisor and Owner confirmation each time;
- the active kernel contains no Stage, Level, Verification role, Patrol, fixed-model,
  or 2.x runtime-control dependency;
- every CLK Skill has one narrow purpose and a clear invocation boundary;
- repository validation and focused scenario tests pass; and
- the installed Skill collection matches the accepted repository release.

## 16. Non-goals

CLK 3.0.0 does not:

- replace or fork SLK;
- introduce a general graph scheduler;
- support dependent same-cycle construction Chains;
- define product-specific interface content;
- require every temporary environment value to become a product setting;
- add routine Owner approvals inside an active Run; or
- automatically start the next CLK Run.
